# 在场探测（排除法）

判断家里有没有人，**不装 App、不买硬件**。客人和没装 App 的家人也要能测到 —— 这条排除了
手机 GPS 方案（HA Companion App 只覆盖装了它的人）。

## 思路

把常驻家电列成白名单，凡是出现在局域网但不在白名单里的设备，就认定是人的手机/平板。

手机普遍开随机 MAC，**结构上永远撞不进白名单**，排除法因此自我强化 —— 不需要认识每一台手机。

> ⚠️ **2026-08-28 已重构为事件驱动状态机，下面这段是旧设计，保留作对照。**
> 旧设计的致命问题见本文末尾「为什么放弃持续扫描」。

```
（旧）每 2 分钟：主动 ping 全网段 → 读邻居表 → 剔除白名单 → 剩下的就是"人"
有陌生设备 → 立刻判"有人"
连续 3 轮没有 → 才判"无人"
```

产出两个 HA 实体（REST API 推送，HA 重启会丢，下一轮补回）：

- `binary_sensor.someone_home`
- `sensor.unknown_devices`（属性里带陌生 MAC 列表）

## 文件

| 路径 | 作用 |
| --- | --- |
| `scripts/presence-scan.sh` | 扫描主体，cron 每 2 分钟 |
| `presence/allowlist.txt` | **决策记录** —— 哪台是家具、为什么。改它 = 一次 commit |
| `presence/install.sh` | 部署，幂等 |
| `/etc/presence-ha-token` | HA 令牌，600，**绝不进 git** |
| `/var/lib/presence/events.tsv` | **历史** —— 到达/离开、在场翻转 |
| `/var/lib/presence/fingerprints.tsv` | **证据** —— 陌生设备首次醒着时自动扫端口 |

脚本直接在 repo 里跑，不复制到 `/usr/local/bin`，避免线上和 repo 两份漂移。

## 四个踩过的坑

**1. 被动 ARP 表不是局域网全貌。**
`ip neigh` 只记录本机最近通信过的主机。小米家电只连云端，从不跟 mail 服务器说话 ——
被动读到 5 台，主动 ping 全网段扫出 10 台。拿被动结果当基线，一开电视就误判"有人回家"。

**2. ping 不通 ≠ 设备离线。**
三星智能显示器待机时，WiFi 模块保持关联并正常应答 ARP（`ip neigh` 显示 REACHABLE），
但主 SoC 睡着，ICMP 和 TCP 全不回。判在线要看**邻居表**，不是 ping 是否成功。
（曾据此误判成"关机掉线"并编了一套推理，被当场戳穿。）

**3. 待机设备的端口指纹是假证据。**
设备睡着时扫端口必然全闭，记下来会永久误导，且首次记录后不再重试。
脚本改成只在设备**真的回 ping** 时才取指纹，否则推迟到下一轮。

**4. 用工具前先 `command -v`。**
曾用 `arping` 做二层探测并得出一整列 `arping=0`，实际上那台机根本没装 arping，
全是假数据。

## 方法的天花板

| 场景 | 结果 |
| --- | --- |
| 客人来访（带手机） | ✅ 不用装 App |
| 家人没装 App | ✅ |
| 手机开随机 MAC | ✅ 反而更准 |
| 手机留家里、人出门 | ❌ 误判"有人" |
| 人在家但没带手机 | ❌ 误判"没人" |
| 新买家电 | ❌ 当成"有人回家"，要补白名单 |

后三行是任何基于 MAC/网络的方案都绕不过的。要闭死得靠 mmWave 存在传感器（如 Aqara FP2），
或把已经在网里的那台 EZVIZ C6N 摄像头接进 HA 用移动侦测。

## 网络看门狗

`scripts/network-watchdog.sh` 由两个脚本合并而来（2026-08-25）：原来的
`~/network-watchdog.sh`（ping 8.8.8.8 失败就重启 Clash）和新加的 wifi-watchdog
（网关不可达就重置网卡）。两个并存会在网关断开时同时动手互相打架，合并成分层决策树：

```
网关不通              → 二层问题，重置无线网卡
网关通 / 国内 DNS 不通 → 路由器或宽带，本机修不了，只记日志
国内通 / 8.8.8.8 不通  → Clash 或 DNS 劫持，重启 Clash → 仍不通则重置 resolv.conf
```

每层只用对症的手段，不会拿网卡重置去治代理故障。

# 多信号融合与「学习」

## 现状：没有模型

跑的是规则 + 一个网格搜索出来的阈值：

| 层 | 是什么 |
| --- | --- |
| 网络排除法 | 硬规则：白名单外有设备 = 有人 |
| 去抖 | 固定常数，连续 3 轮 |
| `quiet_s` 阈值扫描 | 唯一沾边的——单特征单阈值穷举，即 decision stump |

## 信号分层

**强证据**（必须有人动手才会变）：门锁事件、门铃、门状态、台灯开关、开灯次数、
香氛机氛围灯、水壶被提起、电视、小爱音箱。

**弱证据**（可能是走时没关，不能单独当依据）：空调、加湿器。

派生特征 `quiet_s` = 距上次任何强证据变化的秒数，单一最有用的特征。

⚠️ 分类必须用**精确 entity_id**。曾用子串 `_light` / `lamp35` 匹配，把台灯的 20 个
设置项（`delay_time`/`focus_time`/`rest_time`/`nobody_time`/`pir_en`…）和空调、网关的
**指示灯**全划成了强证据——那些是配置和设备自身状态，跟有没有人无关。33 个里 20 个是垃圾。

## 已发现的复合特征

**离家签名**（2026-08-25 10:35 实测）：同一秒内 台灯 off + 香氛机氛围灯 off + 门锁事件。
任何单一信号都读不出语义（门锁不分进出，台灯可能是天亮自动关），三个同时出现才唯一。
这是从数据里看出来的，不是设计出来的——多信号融合的价值证明。

## 评估：必须按转换，不能按样本

样本每 2 分钟一条，一天 720 条，但真实信息只有**两次进出**。按样本算准确率会虚高到
没有意义——「永远猜没人」在出门 10 小时的数据上就有 83%。

`label.py --stats` 因此按状态转换评估：几次进出被检测到、延迟中位数、漏报、误报，
并同时打印「傻瓜基线」提醒该数字不可信。

## 该走的顺序（别跳级）

1. **单阈值 decision stump** — 现在就有，1 个参数
2. **浅决策树 depth 2–3** — 约 50 次进出后。能打印出来读，凌晨被叫醒也看得懂
3. **逻辑回归** — 想要概率而非硬判时；权重可直接检查

**不该用**：随机森林 / GBDT / 神经网络。不是保守，是信息量撑不起来——十来个特征、
几十个参数去拟合一天 2 bit 的真实信息，只会把噪声背下来，且出错时无法调试。

## 更贴合的结构：事件驱动状态机

在场不是 i.i.d. 分类问题，是带转换的状态机：

```
状态: 有人 / 无人
转换: 门从外侧开 → 有人      （门锁硬事件）
      门从内侧开 → 可能没人
      强证据实体变化 → 有人   （必须有人动手）
      静默超过 T → 没人
```

要估的只有静默阈值 T 和各信号权重。先把状态机写对，再用数据调这几个参数，
比套任何模型都实在。

## 标注

- `scripts/label.py "起" "止" home|away` — 事后按时间段补，零摩擦，推荐
- `input_boolean.home_truth` — HA 里的实时开关，进出时拨一下

事后补和实时拨的标注质量完全一样（都是给历史数据打标签），所以别为了实时性增加摩擦。

## 待办

- 门锁 `操作方式/操作ID/操作位置/锁动作` 编号未解码。需要带标注的进出样本反推：
  出门/进门时刻前后各取一条事件，`操作位置` 的两个取值就对应里侧/外侧。
- 台灯有 PIR（`pir_en=on`，`nobody_time=Nobody 20 Minutes`）但**感应结果没暴露成实体**。
  间接可用：台灯自己熄灭 = PIR 判定 20 分钟无人。

# 为什么放弃持续扫描（2026-08-28 重构）

## 旧设计的致命问题

网络状态**直接驱动**在场判定。手机半夜休眠掉线 6 分钟 → 判定翻 `away` → 手机醒来重连
→ 又翻 `home` → 触发回家欢迎仪式 → **音箱说话、灯亮，人被吵醒**。

网络本身会抖，不能直接当状态。这不是调去抖参数能解决的——去抖只能拖慢翻转，
不能消除翻转。

## 新设计：门锁是唯一的状态转换触发器

核心前提：**没有开门就不可能有人进出**。所以状态只在门锁事件后才允许改变。

```
门锁 位置=2（外侧指纹开门）→ 立刻 home
    指纹开门本身就是「有人进来了」的确凿证据，不需要等网络（实测滞后 19 秒）

门锁 位置=1（内侧旋钮开门）→ 进入 leaving 判定，15 分钟窗口内密集查网络
    开门 ≠ 离开（2026-08-27 00:08 那次只是开了下门）
    陌生设备连续 2 轮为 0 → away
    窗口内一直有设备      → 判定没走，保持 home

没有门锁事件 → 状态不变，且不扫网
```

手机掉线多久都不影响状态——没有门锁事件，状态就不会变，欢迎仪式自然不会误触发。

**兜底**：`home` 状态下陌生设备连续 60 分钟为 0（比如漏了门锁事件）才慢速翻 `away`。
阈值故意定得很长——宁可慢，也不能抖。这条路径永远不会在几分钟内翻转。

**扫描量**：720 次/天 → 约 80 次/天。

## 测试

`scripts/test-presence.sh`：假 HA（本地 http server）+ `FAKE_UNKNOWN` 钩子，
跑 4 个场景 9 项断言。改这个状态机前后都要跑。

测试当场抓到两个 bug：`DIR` 写死导致普通用户跑不了；**测试会污染生产状态文件**。
两者都已修（`DIR` 可覆盖，测试用临时目录）。

## 设备分类的实证（2026-08-28）

`events.tsv` 的进出模式把设备分成了三类：

| 设备 | 模式 | 结论 |
| --- | --- | --- |
| `a2c0dde5a472` / `9e2b46ec1630` | 离开时刻 10:56 / 11:08，与门锁出门 10:52 / 11:04 完全对应 | **两台手机，真信号** |
| `AA:BB:CC:DD:EE:FF`（Intel） | 每晚回家后几分钟上线，**凌晨 2:18/2:24 掉线**（那时人在家） | 笔记本休眠，**已加白名单** |
| `a4:ba:70:...` / `ae:f1:62:...` | 短暂出现又消失 | 手机轮换随机 MAC 的产物 |

Intel 那台值得记一笔方法论：数据**无法区分**「被带出门」和「一直在家睡觉」两种假设，
但两种假设下的正确动作**都是放行**。这类问题应该先问「如果答案是 A 我怎么做、是 B 又怎么做」，
两边动作一样就不必去分辨。

**随机 MAC 会定期轮换**，所以历史里会出现多个不同的「人的设备」。这对状态机无害
（只数个数不认身份），但意味着永远无法用 MAC 做 per-person 识别。

# 设备的三分类（2026-08-28）

起因：早上用户出门时忘带了一台手机。那台留在家的手机让「所有陌生设备都消失」这个
判据永远等不到成立，系统判定「没走」，空调没关。

排查时我一度误判成 ARP 陈旧记录，理由是那台设备 ping 不通。**差点据此把判据从
「有 ARP 表项」改成「必须应答 ping」——那会是个严重得多的 bug**：手机在家息屏时
同样不回 ICMP，改完之后每晚手机息屏都会被判成没人，空调半夜被关。
是用户说了实话（"我忘带了一个手机"）才拦下来。

**教训：看到不符合预期的现象时，先确认真实情况，再改代码。**当时手上有更简单的
验证途径——问一句。

## 分类

| 类别 | 文件 | 含义 | 计入 someone_home | 计入 guest_devices |
| --- | --- | --- | --- | --- |
| 家具 | `allowlist.txt` | 从不代表人（路由器、电视、网关、常驻笔记本…） | ✗ | ✗ |
| 必带 | `carried-devices.txt` | 出门一定带在身上 → 最贴近「本人在不在」 | ✓ | ✗ |
| 本人其他设备 | `own-devices.txt` | 属本人但不一定带（第二台手机） | ✓ | ✗ |
| 真·客人 | （以上都不是） | 别人的设备 | ✓ | ✓ |

关键在于把「自己忘带的手机」和「客人的手机」分开——之前两者行为一样，
但期望完全相反：忘带自己的手机应该照常关空调，来了客人则不该关。

## 隐私 MAC 的稳定性（实测）

两台手机的随机 MAC 在 08-25 → 08-28 三天内**没有变化**，说明是「每个 WiFi 固定一个
隐私 MAC」而非每次连接都换，因此可以直接按 MAC 跟踪个体。

但重置网络设置或换机时会变。表现是：必带设备永远「不在网」，而 someone_home 却一直
有其他陌生设备。脚本检测到该组合连续 30 轮会打 WARN 日志提示更新 `carried-devices.txt`。
不加这个提示的话，MAC 一变就变成「永远判定不在家」且毫无征兆。

## 出门关空调的完整判据

```
触发  必带手机 on → off
条件  空调不是已关 且 客人设备数 = 0 且 客厅 PIR 最近 10 分钟无活动
```

| 场景 | 必带 | 客人 | 结果 |
| --- | --- | --- | --- |
| 出门，什么都没忘 | off | 0 | 关 ✓ |
| 出门，忘带第二台手机 | off | 0 | 关 ✓（08-28 修复的场景） |
| 出门，有客人在家 | off | ≥1 | 不关 ✓ |
| 在家，手机息屏掉线 | on | 0 | 不触发 ✓ |

## 测试日志污染

`test-presence.sh` 曾用 `logger -t presence-scan` 写进生产 journal，排查真实问题时
假的「内侧开门」混在真事件里，差点被当成真的。已改为 `LOG_TAG=presence-scan-test`。

# 离开判定的三段式（2026-08-29）

## 起因

08-29 实测：13:17:24 门锁内侧开门（出门），但必带手机直到 **13:54** 才被检出离网，
空调因此多开了 37 分钟。前几天的滞后只有 3~4 分钟。

原因不是网络变慢，是**扫描节奏**：

```
13:17  进入 leaving，15 分钟密集窗口内每 2 分钟扫一次
13:32  窗口到期，手机仍在网 → 旧逻辑判定「没走」，扫描退回 20 分钟一次
13:54  下一次兜底扫描才发现手机早就不在了
```

手机实际是在 13:32~13:54 之间离网的（人在楼下/电梯里 WiFi 还连着），**超出了 15 分钟窗口**。

## 修正：窗口到期 ≠ 结论

旧逻辑把「密集窗口到期」当成了「判定没走」。但窗口到期只说明**还没确认**，
不说明**没走**。改成三段：

```
leaving    密集期   15 分钟，每 2 分钟扫一次
watching   观察期   2 小时，每 6 分钟扫一次   ← 新增
none       常态     每 20 分钟兜底扫一次
```

密集期到期转观察期而不是放弃；观察期内任何时候确认归零都判 away；
观察期也到期了，才真的判定「没走」。

代价很小：观察期每 6 分钟一次，2 小时也就 20 次扫描。

## 相关 bug

第一版把观察期的扫描判断写在了 `tick_prev` 赋值**之前**，导致观察期永远不扫描。
`bash -n` 查不出这类顺序问题——变量未定义时 `${tick_prev:-0}` 静默取 0，
恰好让条件偶然成立/不成立，不会报错。靠新增的场景 5/6 测试才暴露出来。
